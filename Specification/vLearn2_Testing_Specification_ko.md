# 테스트 명세서

**프로젝트:** vLearn2 — 제품명 *Virtual Foreign Language* (VFLS)
**문서 종류:** 테스트 명세서 / 테스트 계획
**버전:** 1.0 (초안)
**작성일:** 2026-05-22
**근거:** `C:\project\vLearn2` 조사 결과 및 동반 시스템 설계·요구사항
명세서를 바탕으로 작성.

---

## 1. 개요

### 1.1 목적

본 문서는 vLearn2 시스템의 테스트 전략, 테스트 환경, 현재 커버리지
기준선, 계획된 테스트 케이스를 정의한다. 시스템이 요구사항
명세서(SRS)에 명시된 요구사항을 충족하는지 검증하기 위한 기준
문서이다.

### 1.2 범위

테스트는 네 개의 모든 서브시스템 — NestJS 백엔드, Next.js 관리자
패널, Flutter 앱, DataManage 도구 — 을 단위, 통합, 종단간(E2E),
수동 테스트 수준에 걸쳐 다룬다.

### 1.3 참고 문서

- vLearn2 시스템 설계 명세서(SDS).
- vLearn2 요구사항 명세서(SRS) — 요구사항 ID `FR-*`, `NFR-*`가 본
  문서에서 추적된다.
- 백엔드 OpenAPI 명세(`/api/docs`).

### 1.4 테스트 케이스 표기

테스트 케이스는 `TC-<영역>-<번호>`로 식별한다. 각 케이스는 검증하는
요구사항을 참조한다. 우선순위는 **P1**(핵심 경로), **P2**(중요),
**P3**(부차)이다.

## 2. 테스트 전략

### 2.1 테스트 수준

| 수준 | 목표 | 주요 도구 |
|------|------|-----------|
| 단위(Unit) | 개별 함수/클래스를 격리하여 검증 | Jest(백엔드, 관리자), `flutter_test`(앱), 스모크 테스트 바이너리(DataManage) |
| 통합(Integration) | 실제 협력 대상(DB, API)에 대해 모듈 검증 | Jest + `supertest` + 임시 PostgreSQL |
| 종단간(E2E) | 서브시스템에 걸친 전체 사용자 여정 검증 | API 주도 E2E; UI 자동화(계획) |
| 수동/탐색적 | UX, 기기, 음성, 설치 흐름 검증 | 테스트 차터 기반 수동 패스 |

### 2.2 서브시스템별 접근

- **백엔드** — 모든 비즈니스 로직을 소유하므로 자동화 테스트의 최우선
  대상이다. 전략: 서비스와 가드를 단위 테스트하고, 컨트롤러를
  `supertest`로 임시 PostgreSQL에 대해 통합 테스트하며, 인증·RBAC·회화/
  채점 흐름을 가장 집중적으로 다룬다.
- **관리자 패널** — `lib/` 유틸리티를 단위 테스트하고, 폼·테이블에
  대한 컴포넌트 테스트를 추가하며, 로그인과 한 가지 CRUD 흐름에 대한
  E2E 스모크 패스를 추가한다.
- **Flutter 앱** — `core/` 로직(가드, datapack, 모델 레지스트리,
  토큰 저장소)을 단위 테스트하고, 핵심 화면에 대한 위젯 테스트와
  인증 상태 기계·라우터 리디렉션에 대한 프로바이더 테스트를 추가한다.
- **DataManage** — 기존 스모크 테스트 바이너리를 Flutter `datapack`
  테스트로 검증되는 pack → sign → unpack 왕복으로 확장한다.

### 2.3 진입 및 종료 기준

**진입 기준**(빌드가 테스트 주기에 들어갈 준비가 됨):

- 서브시스템이 깨끗하게 컴파일/빌드된다.
- 린트와 타입 검사가 통과한다.
- 테스트 환경(§3)이 프로비저닝되었다.

**종료 기준**(테스트 주기 완료):

- 모든 P1 테스트 케이스가 통과한다.
- 미해결 P1 결함이 없다.
- P2/P3 실패는 분류되어 수정되거나 기록된 면제와 함께 수용된다.
- 커버리지가 §7의 목표를 충족한다.

### 2.4 회귀 전략

모든 결함 수정에는 수정 전 실패하고 수정 후 통과하는 테스트가
동반되어야 한다. 전체 자동화 스위트는 모든 변경에 대해 CI에서
실행되어야 한다(§3.3 참조).

## 3. 테스트 환경

### 3.1 백엔드 / 통합 환경

- Node.js 22+.
- 임시 PostgreSQL 16 인스턴스(`docker-compose.yml` 서비스 또는 CI
  서비스 컨테이너).
- 폐기용 비밀값과 전용 테스트 데이터베이스를 가진 테스트 `.env`;
  실행 전 마이그레이션 적용; 필요 시 시드 데이터 로드.
- AI 제공자는 스텁/모킹하여 테스트가 결정론적이고 오프라인이도록 한다.

### 3.2 Flutter 환경

- Flutter 3.41.x 툴체인.
- 단위/위젯 테스트용 `flutter test`(헤드리스).
- `.ddp` datapack 테스트의 경우 DataManage 바이너리와 CA 파일이
  존재해야 하며, 그렇지 않으면 해당 테스트는 자체적으로 건너뛴다.
- 최소 Android 기기 1대(SDK 24 및 최신 SDK)와 Windows 데스크톱 1대에서
  수동 기기 테스트.

### 3.3 지속적 통합

GitHub Actions 워크플로가 서브시스템별로 실행된다(경로 필터링).

- `backend_ci.yml` — PostgreSQL을 프로비저닝하고, 린트·빌드·단위
  테스트와 (비차단) E2E를 실행한다.
- `admin_ci.yml` — 린트·타입체크·빌드를 실행한다.
- `flutter_ci.yml` — 포맷 검사·분석·테스트와 디버그 빌드를 실행한다.

> **조치 항목:** CI는 `master`/`dev`에서 트리거된다. 기본 브랜치는
> `main`이다. 변경이 실제로 테스트되도록 트리거를 정렬할 것. 백엔드
> E2E 단계는 현재 비차단(`|| true`)이며, 안정화되면 차단으로 전환할
> 것.

### 3.4 테스트 데이터

- 시드 데이터: 시드 러너를 통한 기본 업적, 앱 설정, 코스, 페르소나,
  시나리오.
- 픽스처 계정: 학습자 1명, 서브 관리자 1명(제한 권한), 슈퍼관리자 1명.
- 픽스처 회화: 채점 테스트를 위한, 알려진 메시지 시퀀스를 가진 시나리오
  세션 1건.

## 4. 현재 커버리지 기준선

작성 시점의 기존 자동화 테스트:

| 서브시스템 | 테스트 파일 | 현재 커버 범위 |
|-----------|-------------|----------------|
| 백엔드 | `ai/prompt-builder.service.spec.ts`, `guard/content-guard.service.spec.ts`, `test/app.e2e-spec.ts` | 프롬프트 빌더 로직, 콘텐츠 가드 로직, `GET /health` 스모크 |
| 관리자 패널 | `lib/__tests__/env.test.ts`, `flag-catalog.test.ts`, `utils.test.ts` | 순수 `lib/` 유틸리티 |
| Flutter 앱 | `test/datapack/installer_test.dart`, `unpack_test.dart`, `test/guard/content_guard_test.dart`, `test/storage/model_registry_test.dart` | datapack 설치/해제, 콘텐츠 가드, 모델 레지스트리 |
| DataManage | `manifest_smoke_test.cpp`, `packer_smoke_test.cpp`, `session_smoke_test.cpp` | 매니페스트·패커·세션 스모크 점검 |

**평가:** 커버리지는 얕고 순수 로직 단위에 치우쳐 있다. 비즈니스
로직의 대부분 — 백엔드 컨트롤러/서비스, 인증, RBAC, 회화 및 채점,
관리 작업, 모든 Flutter 화면 — 은 현재 테스트되지 않는다. §5–6은
이 격차를 메우는 데 필요한 테스트 케이스를 정의하고, §7은 커버리지
목표를 설정한다.

## 7. 커버리지 목표 및 격차 해소

### 7.1 목표

| 서브시스템 | 현재 | 목표 |
|-----------|------|------|
| 백엔드 — 서비스 및 가드(단위) | 2개 파일 | 서비스·가드의 라인 커버리지 ≥ 80% |
| 백엔드 — 컨트롤러(통합) | health 스모크만 | 모든 엔드포인트에 정상 경로 + 인증/검증 테스트 각 1개 이상 |
| 관리자 패널 | `lib/` 유틸만 | `lib/` ≥ 80%; 폼·테이블별 컴포넌트 테스트; E2E 스모크 1개 |
| Flutter 앱 | core 로직 4개 파일 | `core/` 로직 ≥ 70%; 스플래시·인증·회화·리포트 위젯 테스트; 인증·라우터 프로바이더 테스트 |
| DataManage | 스모크 바이너리 3개 | 전체 pack/sign/encrypt/compress 왕복 + 변조 거부 |

### 7.2 우선순위별 격차 해소 계획

1. **P1 — 백엔드 인증 및 RBAC 통합 테스트.** TC-AUTH-*,
   TC-ADM-10/11/12, TC-NFR-SEC-1/2/3. 위험도가 가장 높고 현재
   미테스트.
2. **P1 — 회화 및 채점 흐름.** TC-CONV-*, TC-SCORE-*, AI 대체 경로
   포함(TC-CONV-10, TC-NFR-REL-2).
3. **P1 — 관리 변경 + 감사 원자성.** TC-ADM-14/15, TC-NFR-REL-3.
4. **P2 — Flutter core + 핵심 위젯 테스트.** 토큰 저장소(Windows 캐시
   경로 포함), 라우터 리디렉션, 인증 상태 기계, 회화 화면.
5. **P2 — 관리자 패널 컴포넌트 + E2E 스모크.**
6. **P3 — 뉴스, 리더보드, 통계, 지역화.**

### 7.3 추적성

SRS의 모든 `FR-*` 및 `NFR-*`는 본 문서의 최소 한 개 `TC-*`에
매핑되어야 한다. §5–6은 *요구사항* 열에서 그 매핑을 제공한다. 신규
요구사항은 대응하는 테스트 케이스 없이 수용되어서는 안 되며,
추적성은 매 릴리스마다 검토되어야 한다.

## 8. 결함 관리

- 결함은 심각도(S1 차단 … S4 미관), 재현 단계, 환경, 관련
  `TC-*`/`FR-*` ID와 함께 기록한다.
- **S1/S2** 결함은 릴리스를 차단한다. **S3/S4**는 기록된 면제와 후속
  티켓과 함께 출시될 수 있다.
- 모든 수정에는 회귀 테스트를 추가한다(§2.4 참조).
